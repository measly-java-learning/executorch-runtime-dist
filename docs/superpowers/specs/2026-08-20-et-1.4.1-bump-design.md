# Bump the ExecuTorch pin to v1.4.1 — Design

**Status:** design, not yet planned
**Release tag to cut:** `v1.4.1-1`
**Current latest release:** `v1.3.1-10`
**Verified against:** ExecuTorch `v1.3.1` (`e2f18eb`) → `v1.4.1` (`e4d02f4`), read from the
upstream tags directly (`git diff v1.3.1 v1.4.1`, `gh api .../contents/...?ref=v1.4.1`)

## Goal

Ship the full release matrix built against ExecuTorch `v1.4.1` — all three variants (`bare`,
`logging`, `devtools`) on `linux-x86_64` and `linux-aarch64`, plus `logging` on `windows-x86_64`
and `windows-x86_64-static` — as tag `v1.4.1-1`, with the recipe's vendored patch set regenerated so the
`workspace_size_bytes` consumer contract survives the move.

## Scope

**In:** the ET pin, the torch pin that rides with it, the regenerated
`patches/et-xnnpack-workspace-size.patch` and its hermetic fixtures, the version/torch strings
that are hardcoded rather than derived, and the user-facing docs that quote a version.

**Out, deliberately:**

- **The OpenVINO bundle stays at `2025.4.1`.** ET's OpenVINO backend changed README-only between
  the two tags, so nothing forces a bump. `scripts/lib/openvino.sh` and the C10 asset are
  untouched.
- **`.build-image` stays on its current manylinux digest.** Nothing in v1.4.1 raises a toolchain
  floor (`cmake_minimum_required` is 3.24 at both tags).
- **The dead install-destination `sed` stays in place** this release — see Follow-ups.
- **Handover docs are not swept.** `docs/handover-to-engine.md` and
  `docs/handover-windows-static-cxx17.md` are point-in-time snapshots of what was handed over,
  not live contracts; rewriting their version strings would make them lie about when they were
  written. Same for `docs/superpowers/{specs,plans}/*` and `spike/*`, which are historical.

## 1. Regenerate the vendored patch set

This is the only part that is engineering rather than substitution.

`patches/xnnpack-workspace-size-accessor.patch` needs **no change**: it targets
`include/xnnpack.h` and `src/runtime.c` in the XNNPACK submodule, whose pin is byte-identical
across the two ET tags.

`patches/et-xnnpack-workspace-size.patch` **fails to apply**. Measured with `git apply --check`
against the v1.4.1 sources:

- `backends/xnnpack/runtime/XNNPACKBackend.h` — **hunk fails.** Upstream inserted
  `packed_cache_path_option_key` and `save_weight_cache_on_disk_option_key` between
  `weight_cache_option_key` and `workspace_sharing_mode_option_key`, which is exactly our anchor
  window.
- `backends/xnnpack/runtime/XnnpackBackendOptions.cpp` — **hunk fails.** Upstream added
  `packed_cache_path` branches to both `get_option` and `set_option`, in the same `else if` chains
  our branches join.
- `backends/xnnpack/runtime/XNNWorkspaceManager.cpp` — applies at **offset +2**.
- `XNNWorkspace.h` and `XNNWorkspaceManager.h` — apply clean.

All four are **context drift, not semantic conflict**. Upstream added neighbouring options; it did
not add a size accessor and did not restructure what our patch touches. The
`workspace_size_bytes` key, its read-only semantics, and
`docs/xnnpack-workspace-size-consumer.md` are unchanged by this release.

### How the patch is regenerated

From a **pristine v1.4.1 tree**, never from the working checkout.
`/home/corey/workspace/executorch` is dirty: `build-runtime.sh` applies its seds and patches
in place, so `git status` there already shows all five patched files plus four modified
`CMakeLists.txt`. A patch generated from an already-patched tree is silently wrong in a way no
test catches.

Use a `git worktree` at `v1.4.1` off the existing clone — it shares the object store, so only
the XNNPACK submodule needs initialising for the accessor patch's target dir. Re-apply the five
hunks against the new anchors, then `git diff` back out into `patches/`.

### Fixture refresh, same commit

`test/fixtures/etpatch/` holds verbatim upstream copies so
`test/patch_et_xnnpack_workspace.test.sh` runs hermetically. Keeping them in lockstep with
`patches/*.patch` is a stated contract in CLAUDE.md — a stale fixture makes the patch test pass
while the real build fails.

Refresh from v1.4.1 (changed upstream): `XNNPACKBackend.h`, `XNNWorkspace.h`,
`XNNWorkspaceManager.cpp`, `XnnpackBackendOptions.cpp`, `XnnpackBackendOptions.h`.

Leave alone: `XNNWorkspaceManager.h` (unchanged upstream between the tags), `xnnpack.h` and
`runtime.c` (submodule pin unmoved). Copying them again is harmless but produces no diff.

Update `test/fixtures/etpatch/README.md` — it names "ExecuTorch v1.3.1 (commit e2f18eb)" as the
source of the copies.

## 2. The pin and torch sweep

Version-derived machinery needs **no edit**: asset and tarball naming (`scripts/lib/naming.sh`),
pin generation (`gen-pin.sh`, `discover-pin-rows.sh`), version derivation
(`derive-version.sh`), and gate classification all read `etver` out of the release tag.

Hardcoded strings that must move:

| File | Change |
|---|---|
| `build-runtime.sh:19` | `DEFAULT_ET_TAG="v1.3.1"` → `"v1.4.1"` |
| `build-runtime.sh:20` | `TORCH_SPEC="torch==2.12.0+cpu"` → `"torch==2.13.0+cpu"` |
| `build-runtime.sh:28` | usage text: "default v1.3.1" |
| `scripts/package.sh:68` | `TORCH_VERSION="2.12.0+cpu"` — the BUILDINFO provenance field (C5) |
| `scripts/gen-requirements.sh:41` | the `torch==2.12.0+cpu` comment baked into generated requirements |
| `.github/workflows/release.yml:333` | release-notes text `(torch 2.12.0+cpu)` |
| `test/buildinfo.test.sh` | `TORCH_VERSION=2.12.0+cpu` in five places |

Then regenerate `requirements/*.txt` with `scripts/gen-requirements.sh` followed by
`scripts/compile-requirements.sh`. The `.in` files deliberately track (not pin) numpy and pytest
because upstream chooses them, so the compiled pins are expected to move on their own with the
new torch.

**Test literals are left alone on purpose.** `v1.3.1-2` in `test/classify_gate.test.sh` and
`1.3.1` in `test/discover_pin_rows.test.sh` are arbitrary fixture values exercising tag parsing
and filename discovery, not pins. Rewriting them would enlarge the diff without testing anything
new.

## 4. Verification

Four rungs, in order:

1. **`bash test/run.sh`** — hermetic, ~2s. The patch test now runs against the refreshed
   fixtures, which is what proves the regenerated patch matches real v1.4.1 anchor text rather
   than matching a stale copy of itself.
2. **PR → `extras-gate` in `full` mode.** Classification lands there automatically: any
   `build-runtime.sh` change forces `full`, and there is no published 1.4.1 release for tier1/2
   to download anyway. That is a full linux-x86_64 release dry-run — ET build, extras, AOT
   round-trip, OpenVINO fixture run, relocatability, CRT and USDT guards, and
   `test/xnnpack_workspace_run.sh`, the behavioural probe that proves the regenerated patch is
   reachable at runtime and reflects a live arena. The post-build `nm` guard on
   `xnn_get_workspace_size` independently proves the patch survived compilation.
3. **Windows, locally on `winbox`.** Build `logging` at both `windows-x86_64` (/MD) and
   `windows-x86_64-static` (/MT) against v1.4.1 before tagging. This is the highest-risk
   surface in the release and the PR gate does not cover it: `full-build`, `full-aot` and
   `full-gates` all run on `ubuntu-latest`, so Windows is otherwise first compiled by the release
   tag itself — against ~1,200 lines of XNNPACK runtime MSVC has never seen, on a new torch minor.
4. **`linux-aarch64` rides on the release tag.** Accepted risk: a failure there costs a re-roll
   to `v1.4.1-2`, which is what `pkgrev` exists for.

## 5. Landing

One branch, `chore/et-1.4.1`, two commits:

1. `patches/*.patch` + `test/fixtures/etpatch/*` + fixture README — together, per the lockstep
   contract.
2. The pin, torch, requirements and docs sweep.

Then: PR → full gate green → winbox check → merge → `git tag v1.4.1-1 && git push origin v1.4.1-1`.

## Follow-ups (filed as issues, not done here)

1. **Retire the dead install-destination `sed`.** pytorch/executorch#20709 is fixed in v1.4.1, so
   `build-runtime.sh:182-198` now prints "nothing to patch" on every build, forever. Removing it
   is a behaviour change to the recipe and deserves its own PR and its own full gate rather than
   riding along inside a pin bump.
2. **Evaluate ET 1.4.1's new XNNPACK weight-cache surface.** v1.4.1 adds
   `packed_cache_path_option_key`, `save_weight_cache_on_disk_option_key` and a
   `XNNWeightsCacheManager` that persists the packed weight cache to disk. This overlaps
   conceptually with the `lstm_xnn_cache` USDT probes in `extras/lstm` and with the memory
   accounting `workspace_size_bytes` serves. Worth deciding whether any of it becomes a published
   consumer contract — the upstream header marks `save_weight_cache_on_disk` EXPERIMENTAL, so the
   answer may be "not yet".
