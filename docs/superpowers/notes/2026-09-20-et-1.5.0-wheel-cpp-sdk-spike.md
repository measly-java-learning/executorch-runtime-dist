# Spike: can the ExecuTorch 1.5.0 wheel's C++ SDK replace our Linux build?

**Date:** 2026-09-20
**Verdict:** Not as shipped, but the gap is now *headers only* and every missing
header is recoverable from a tag-matched checkout. Windows, the workspace-size
accessor, and the third-party notice sweep remain ours regardless.

## Why this was run

ExecuTorch 1.5.0's release notes say: *"Expanded the Python wheels into a C++
SDK, with linkable libraries for the CUDA, Core ML, MLX, OpenVINO, and Qualcomm
delegates"* and *"Added a C++ SDK to the Python wheel and split the runtime from
the Python bindings extension."*

This repo exists because upstream shipped no relocatable `-fPIC` desktop
artifact. That sentence is upstream claiming to have closed the gap, so it
needed measuring rather than assuming.

## Where the binaries actually are

**Not on the GitHub release.** `v1.5.0` carries exactly two assets, both CMSIS
packs for embedded Arm:

```
PyTorch.ExecuTorch.1.5.0.pack   1,793,072
PyTorch.ExecuTorch.pdsc           145,040
```

The C++ SDK is inside the **PyPI wheel**. Platforms: `manylinux_2_28` x86-64 and
aarch64, `macosx_14_0_arm64`, `win_amd64`; cp310 through cp314.

Subject under test: `executorch-1.5.0-cp312-cp312-manylinux_2_28_x86_64.whl`
(19,024,215 bytes).

```
executorch/lib/libexecutorch.so              427K   SONAME set, RUNPATH $ORIGIN:...
           libexecutorch_kernels_optimized.so  10M
           libexecutorch_kernels_quantized.so 299K
           libexecutorch_backend_xnnpack.so   2.7M
           libexecutorch_backend_openvino.so   27K
           libexecutorch_backend_qnn.so       255K
           libexecutorch_etdump.so             75K
           libexecutorch_threadpool.so        190K
executorch/lib/cmake/executorch/executorch-config.cmake   896 lines
executorch/share/cmake/executorch-config.cmake            (same, root marker)
executorch/include/executorch/{runtime,extension,devtools}/   120 headers
```

Shared libraries, so PIC by construction — the exact property this repo was
built to provide. Floors: `GLIBC_2.27`, `GLIBCXX_3.4.21`. 419 exported symbols
from `libexecutorch.so`, including `Module::load_method`, `Method::execute`,
`register_backend`.

The config is thoughtful and clearly aimed at consumers like us. Its own
comments note the Python extension is deliberately **not** offered as a link
target (its undefined CPython symbols only resolve inside an interpreter), and
that *"a project building a custom operator links the runtime, which is where
the operator registry lives once the runtime is split out of the extension."*

## Windows: nothing

`executorch-1.5.0-cp312-cp312-win_amd64.whl` ships **no runtime `.lib` or
`.dll`**. Only two AOT-side plugins:

```
executorch/extension/llm/custom_ops/custom_ops_aot_lib.dll
executorch/kernels/quantized/quantized_ops_aot_lib.dll
```

No `executorch.lib`, no CRT-variant split. Our `windows-x86_64` and
`windows-x86_64-static` platforms have no upstream equivalent whatsoever.

## Run A — faithful `--extras-only` against the unpacked wheel

Fails before any compile:

```
--extras-only but <prefix>/lib/cmake/ExecuTorch/executorch-config.cmake is missing;
provide a built/extracted ET prefix
```

The wheel installs to `lib/cmake/executorch/` (lowercase) plus `share/cmake/`.
`build-runtime.sh` hardcodes the `ExecuTorch/` spelling in `CONFIG`. Cosmetic,
but it is the first wall.

### Trap: the CMake package-name case

The wheel's config sets `executorch_FOUND` and `EXECUTORCH_FOUND`. It never sets
`ExecuTorch_FOUND`. On a mis-staged prefix the config correctly detected itself
as broken, printed

```
-- ExecuTorch package at  is missing /include, so nothing can compile against it.
```

and set `EXECUTORCH_FOUND=OFF` — and `find_package(ExecuTorch CONFIG REQUIRED)`
**succeeded anyway**, because CMake checks the `ExecuTorch_FOUND` spelling the
config never writes. A genuinely broken package configures clean and fails much
later at compile time.

Anything adopting this must call `find_package(executorch)`, lowercase.

(The mis-staging was mine: the config locates its root by probing for
`share/cmake/executorch-config.cmake`, which I had not copied. Deliberate design
on their part — a marker rather than a fixed depth, so the same file works from
both install locations.)

## The shim

`extras/CMakeLists.txt` uses the in-tree ET package's bare target names. The
wheel exports namespaced ones. Probing both sets:

```
TARGET MISSING executorch                 TARGET OK executorch::runtime
TARGET MISSING optimized_native_cpu_ops_lib  TARGET OK executorch::kernels_optimized
TARGET MISSING xnnpack_backend            TARGET OK executorch::backend_xnnpack
TARGET MISSING extension_module_static    TARGET OK executorch::kernels_quantized
TARGET MISSING extension_data_loader      TARGET OK executorch::backend_openvino
TARGET MISSING extension_tensor           TARGET OK executorch::threadpool
                                          TARGET OK executorch::etdump
```

The mapping is mechanical. `extension_module_static`, `extension_data_loader`
and `extension_tensor` all collapse onto `executorch::runtime` — `Module::` and
`TensorPtr` symbols are exported straight out of `libexecutorch.so`.

The spike shim (a fake `ExecuTorchConfig.cmake` placed ahead on
`CMAKE_PREFIX_PATH`):

```cmake
find_package(executorch CONFIG REQUIRED PATHS "${_wheel}" NO_DEFAULT_PATH)
macro(_shim name dep)
  if(NOT TARGET ${name})
    add_library(${name} INTERFACE IMPORTED GLOBAL)
    target_link_libraries(${name} INTERFACE ${dep})
  endif()
endmacro()
_shim(executorch                    executorch::runtime)
_shim(optimized_native_cpu_ops_lib  executorch::kernels_optimized)
_shim(xnnpack_backend               executorch::backend_xnnpack)
_shim(extension_module_static       executorch::runtime)
_shim(extension_data_loader         executorch::runtime)
_shim(extension_tensor              executorch::runtime)
_shim(extension_threadpool          executorch::threadpool)
set(ExecuTorch_FOUND TRUE)
```

## Run B — green, and WRONG. Do not trust it.

Run B supplied the missing XNNPACK headers by pointing the include path at
`out-logging/include`. It built clean, the registrar nm-guard passed, and
`lstm_kernel_test` printed `OK`.

It was invalid. `out-logging/include` is a **full ET install prefix**, so it
shadowed ExecuTorch headers as well as supplying XNNPACK ones. The build was a
silent mixture of v1.3.1 headers and v1.5.0 binaries. (`out-logging` was built
from **v1.3.1**, not the v1.4.1 pin — its `.et_commit` is `e2f18eb23`, which
`git describe` reports as `v1.3.1`. See the corrections section below.)

Two concrete consequences:

1. **`xnnpack.h` drift** — 117 changed lines between the two pins: new datatypes
   (`xnn_datatype_qint4`, `qint2`), `xnn_define_static_constant_pad` deprecated
   in favour of a `_v2`, a new `batch_matrix_multiply_nc_f32_qc8w` family. This
   holds for v1.4.1 as well: v1.3.1 and v1.4.1 pin the same XNNPACK commit
   (`1adaa7c7`).

2. **`threadpool.h` is an ABI break — between v1.3.1 and v1.4.0, not 1.4.1 and
   1.5.0.** The `size_t thread_count_` member of `ThreadPool` arrived in
   `e03f777c4`, first shipped in v1.4.0. The header is byte-identical at v1.4.1,
   v1.5.0 and v1.5.1 (blob `b1f0168747`). The diff below is v1.3.1 → v1.5.0:

   ```
   52a53,56
   >   /** Returns the number of threads in the threadpool. ... */
   99a104,105
   >   // The number of threads in the threadpool.
   >   size_t thread_count_;
   ```

   Run B compiled a 1.3.1-sized `ThreadPool` against a `.so` holding the 1.5.0
   layout, then ran it. It printed `OK`. That is exactly how this class of bug
   presents, and it is the single most important thing in this note.

Contrast, counted in the generated `build.ninja`:

```
run B:  out-logging occurrences: 2
run C:  out-logging occurrences: 0    aux-include: 2    wheel-prefix: 16
```

## Run C — green, with fully version-matched headers

Headers sourced three ways, all correct for v1.5.0:

| Source | Provides |
|---|---|
| the wheel's own `include/` | 11 of the 12 ET headers `extras/` needs |
| `google/XNNPACK@92a7ad5` (the submodule pin at tag `v1.5.0`) | `xnnpack.h` |
| `git show v1.5.0:extension/threadpool/threadpool.h` | `threadpool.h` |

```
[22/22] Linking CXX executable etnp_extras_link_probe
-- assert_extras_registered: all extras registrar TUs present: [_GLOBAL__sub_I_etnp_lstm.cpp]
$ LD_LIBRARY_PATH=<wheel>/lib ./lstm_kernel_test
OK: etnp::lstm.out analytic recurrence correct
```

`ldd` on the link probe resolves against the wheel's `.so` files only.

**`pthreadpool` and `cpuinfo` need no special handling** — both are pinned to the
identical commit in v1.4.1 and v1.5.0 (`a56dcd79`, `f9a03241`). Only XNNPACK
moved (`1adaa7c7` → `92a7ad50`).

USDT was not exercised: no `sys/sdt.h` on the spike box, so the build ran
`-DETNP_ENABLE_USDT=OFF` and the guard confirmed `ok: no stapsdt notes (USDT
disabled)`. Orthogonal to the wheel question; `systemtap-sdt-dev` would close it.

## The actual gap: headers, not symbols

| Need | Wheel ships | Tag-matched source has |
|---|---|---|
| `libexecutorch*.so` symbols | yes — all resolved | — |
| 11 of 12 ET headers | yes | yes |
| `extension/threadpool/threadpool.h` | **no** (ships only `threadpool_guard.h`) | yes |
| `xnnpack.h` / `pthreadpool.h` | **no** | yes (submodule) |

Note the shape of the threadpool gap: the wheel **exports**
`executorch::extension::threadpool::get_threadpool()` and **defines** an
`executorch::threadpool` CMake target, but omits the header declaring it. You
can link it; you cannot call it. That reads as an oversight, not a policy — see
the header-gap issue draft.

## Corrections

### Run B's headers were v1.3.1, not v1.4.1 (corrected 2026-10-04)

As first written, this note called run B a mixture of "v1.4.1 headers and v1.5.0
binaries" and attributed the `thread_count_` ABI break to v1.5.0. Both were
wrong. `out-logging/.et_commit` is `e2f18eb23`, which `git describe` reports as
`v1.3.1`. The same holds for `out`, `out-bare` and `out-devtools`. Only
`out-eigen` and `out-tok` are v1.4.1 builds (`e4d02f41f`).

What changes: the `ThreadPool` layout break is v1.3.1 → v1.4.0, so the current
pin (v1.4.1) and v1.5.x agree on `threadpool.h`. What does not change: the
lesson. A mixed-version build printed `OK` and was wrong, and the only reliable
defence is asserting that headers and binaries come from the same tag. The
`xnnpack.h` drift and the `pthreadpool`/`cpuinfo` findings are unaffected
because v1.3.1 and v1.4.1 share all three submodule pins.

The mistake had the same root cause as the next correction: a local prefix's
name says nothing about which ET version built it. Read `.et_commit` before
treating a prefix as a given version.

### No Eigen notice in `out-logging` (found mid-spike)

`out-logging/THIRD-PARTY-NOTICES` holds 36 files and **no Eigen notice**, which
briefly looked like the same gap on our side. It is not.
`assert_shipped_archive_notices` fails against that prefix on six archives
(`libeigen_blas.a`, `libabsl_base.a`, `libsentencepiece.a`, `libre2.a`,
`libpcre2-8.a`, `libtokenizers.a`).

`out-logging` is a **stale July prefix** (dated 2026-07-13) predating both
`b1d7600` (Eigen, #45) and `5e3eaa3` (tokenizers, #52/#53). The current recipe
ships all of these correctly. The guard did its job.

Reinforces the existing rule: a local built prefix is real, but it is a snapshot
of the recipe at the time it was built, not of the recipe on `main`.

## Conclusions

1. **The ET-facing surface of `extras/` is already wheel-compatible.**
   `lstm_kernel_test.cpp` and `link_probe.cpp` compiled against the wheel's own
   headers with no edits. The only unsatisfiable dependency is XNNPACK, because
   the lstm op reaches past ExecuTorch into XNNPACK's C API for its cache.

2. **A hybrid is viable**: wheel for binaries, tag-matched checkout for the few
   unshipped headers. It comes with a hard constraint — the checkout tag and the
   wheel version must be locked together and asserted, because the
   `thread_count_` incident is exactly what drift produces, and it fails
   silently.

3. **Unchanged by 1.5.0**: Windows (no C++ runtime at all), the
   `workspace_size_bytes` accessor (zero hits for `xnn_get_workspace_size`
   across all eight `.so` files), and the notice sweep.

4. **Framing.** This is upstream finally delivering the portability whose
   absence forced this repo into existence. The right response is to push our
   local additions upstream and let this repo shrink to what remains genuinely
   first-party.

## Reproducing

Spike artifacts were scratch-only; nothing was written to the repo. To redo:

```bash
# 1. fetch + unpack the wheel
curl -s https://pypi.org/pypi/executorch/1.5.0/json \
  | python3 -c 'import json,sys;print([f["url"] for f in json.load(sys.stdin)["urls"]
      if f["filename"]=="executorch-1.5.0-cp312-cp312-manylinux_2_28_x86_64.whl"][0])'
# unzip; stage executorch/{include,lib,share} as the prefix

# 2. matched headers
git -C <executorch> fetch --no-tags origin tag v1.5.0 --depth=1
git -C <executorch> show v1.5.0:extension/threadpool/threadpool.h
curl -sfL https://raw.githubusercontent.com/google/XNNPACK/92a7ad501b9516f9fecae119e0146dd1f58e54c1/include/xnnpack.h

# 3. configure extras against the shim, build, run
cmake -B <build> -S extras -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_POSITION_INDEPENDENT_CODE=ON -DETNP_ENABLE_USDT=OFF \
  -DCMAKE_PREFIX_PATH=<shim> -DCMAKE_INSTALL_PREFIX=<prefix>
```

**Always check `grep -c out-logging <build>/build.ninja` returns 0.** That single
check is what separated run C from run B.
